旧桥解析 WebSocket 上的 STOMP 文本帧和 JSON，识别入桌、开局、摸牌、弃牌、副露、宝牌与结算，再转换为 MJAI。其检查要求 `gameType == 0`（日麻），并区分 `gameMode` 的三麻 / 四麻值。因此旧实现能够提供协议参考，不能据此宣称台湾、香港或其他玩法可直接交给日麻模型。

旧 v2 的 LICENSE.txt 是 AGPLv3 附 Commons Clause；v3 使用 Apache-2.0。后续应将旧协议资料与具体实现的来源、许可分别核对，不把旧源码默认当成 v3 的 Apache 代码直接并入。

- **协议能力边界。** 已阅读旧 `AmatsukiBridge` 和对应 MITM 模块。前者围绕牌局事件转 MJAI，后者另有大厅心跳处理；没有角色所有权列表、装备保存或本地装扮持久化实现。不能把它当作现成装扮插件，只能作为后续协议核对的资料。
- **官方装扮分类。** 2026-11-05 官方维护完成公告提到觉醒奖励与限定服装；2026-10-15 公告列出手部样式、动态立直棒、牌背、桌面、对局音乐、名片边框及背景等分类。官方商店介绍另列出多语种语音、贴图、动态立绘和和牌动画。因此角色、皮肤、装备、语音和养成展示需要分别核对，不能统一视作一个“已拥有”开关。
- **真实进度与本地展示。** 官方公告将部分造型与觉醒等级关联。未来原型应只验证本地展示与选择，不伪造服务器的角色养成、抽取或物品数量；是否能独立加载对应视觉和语音资源仍需客户端证据。

## 建议的技术决策

| 客户端检查结果 | 优先验证方式 | 成功标准 |
| --- | --- | --- |
| 角色目录与拥有列表可在本地分别获取，界面能接受本地资料 | 小范围适配目录、拥有状态与装备响应 | 非默认角色 / 皮肤可在原生界面选中，并可重启保存 |
| 列表可展示，但保存时被服务器响应恢复，或进桌另取装备资料 | 增加本地选择存储与自身资料一致性处理 | 大厅、友人房、进桌、牌桌、详情及结算使用同一选择 |
| 原生界面在发送消息前已拒绝选择，需要改本地脚本 | 检查实际脚本形式和资源校验，评估可恢复的客户端补丁 | 已适配版本可安装 / 还原，未知更新拒绝覆盖 |
| 资源本身无法正常加载，或仅有目录而无对应内容 | 暂停扩大解锁范围，重新评估资源可用性 | 不把可点击的空白条目当成已完成 |

以上是条件式方案，不是已经验证的客户端实现。Unity、Lua、IL2CPP 等具体技术栈仍不作为已确认结论；只有检查实际客户端后才选择工具。

第一阶段验收限定为一位角色、一套非默认造型、原生界面选择、友人房与牌桌一致以及重启保存。头像跟随、语音、觉醒外观和全量装饰随后逐项验证。AI 若另行接入，先覆盖日麻三 / 四麻完整开局，不将其他玩法送入日麻模型。

## 本地装扮的初步可行性

结论：值得做小原型，但目前只能确认旧版本游戏消息具备可解析入口，尚不能确认当前装扮列表、保存接口和资源校验方式。AI 桥能解析牌局，不等于已经具备装扮解锁能力。

建议按以下顺序验证：

1. **客户端与资源。** 确认当前 PC 版本、资源更新位置、实际引擎与脚本形式，找角色、皮肤、头像、表情和特效目录。不预设它与掌心或一番街使用相同 Lua 打包方式。
2. **列表与所有权。** 区分全量装扮目录和账号拥有列表，检查未拥有资源是否可加载；只读定位登录、大厅、装备选择和友人房相关消息。调试资料只留本机，不记录登录凭据或完整私人响应。
3. **本地选择与保存。** 将角色 / 皮肤 / 装备选择按账号保存到本机，在客户端应用一致资料；如果服务器拒绝未拥有物品，客户端选择流程需要本地处理，单独改列表可能仍会被回包恢复。
4. **贯通展示。** 同时验证大厅、友人房卡片、进桌介绍、牌桌头像、和牌立绘、详情与重启重载，避免只在大厅显示或进桌恢复默认。其他玩家的真实资料保持原样。
5. **可恢复安装。** 如果最终需要改客户端脚本，按实际资源版本与摘要适配，先备份再替换，遇到未知官方更新停止覆盖；不向分发包加入游戏资源。

若资源已随客户端提供、所有权主要用于本地界面判断，代理响应适配或可恢复的脚本补丁具有可行性。若资源下载本身受服务端资格限制，或脚本 / 资源具有不能适配的签名与加密约束，则需要重新评估范围，不能承诺全量装扮可用。这些是待验证的条件判断。

首个原型宜只覆盖一个角色、一套非默认皮肤及其重启保存，成功后再扩展完整列表、方案、头像与语音。AI 接入可与装扮模块独立实施，但都需要当前客户端消息核实。
